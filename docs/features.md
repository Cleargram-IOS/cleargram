| ✅ `feature__clear-settings-ui` | "Cleargram" entry in Settings, opening `ClearSettingsController` (fork file in `src/swift/ClearGram/DebugSettingsUI/`). Home for every `ClearConfig` toggle. Laid out like stock Telegram settings: a hub of icon rows (rendered with the stock `renderSettingsIcon`) opening per-area screens — Appearance, Chat List, Tab Bar, Chats, Channels, Media & Stickers, Links, Message Menu, Profile, Privacy, Debloat — plus a destructive Reset with a confirmation alert. The screen tree is **data**, declared in `clearRootScreen()` at the bottom of the file — `ClearScreen`/`ClearSection`/`ClearToggle` values with `WritableKeyPath` storage; a generic entry enum handles ids, equality and item construction, so adding an option is one `ClearToggle(...)` line. Unimplemented toggles are declared via `ClearToggle.soon(title:plan:)` and render disabled with the plan as a subtitle. **Build stamp:** the last line on the root screen reads `Telegram 12.9.2 · upstream 6ad963e5b6 · Cleargram 31eac9a` — the upstream release, the commit the patchset is pinned to and the cleargram commit the build was assembled from. Cleargram deliberately has no version number of its own: those three values are what actually identify a build, and unlike a build counter they need no state to maintain and map straight back to the source. **Dirty builds:** an uncommitted tree adds a `+<id>` suffix (`Cleargram 31eac9a+97a74d7`) where the id is a hash of the working-tree patch — `git status --porcelain` + `git diff HEAD` + a `/dev/null` diff per untracked file, so new fork sources count too. That keeps the line an identity rather than a warning light: the same tree always hashes to the same id, and `pnpm sync` archives the patch as `build/dirty-stamps/<commit>+<id>.diff` (gitignored, and appliable as-is), so whatever is running on a device can be reconstructed with `git apply` — which doubles as the recovery path when uncommitted work is lost. A timestamp or a counter would order builds but say nothing about their contents, and a timestamp inside a Bazel input would rebuild the module on every sync. It comes from `ClearBuildInfo`, a fork file that ships with placeholder values and whose worktree copy `pnpm sync` overwrites with the real ones (`writeBuildInfo` in `scripts/lib.ts`, run right after the copy loop that lays the placeholder down — the placeholder is what stops a sync that didn't run from breaking the build). It lives in DebugSettingsUI, next to the screen that reads it: the file changes with every commit, and in TelegramUIPreferences — which nearly everything depends on — that would invalidate the whole tree. No build-time values go in it (a timestamp would rebuild the module on every build), and nothing touches `Make.py`, `Telegram/BUILD` or the plist. |

- `search-by-user-id` — find a group's messages by author when the member list is hidden. **Researched 2026-09-29; the original "RESEARCH NEEDED" note asked the wrong question.** `messages.search` with `from_id` is not blocked by a hidden member list — stock already depends on that: long-pressing a message author and choosing Search goes through `ChatControllerUpdateSearch.swift:85` (`location: .peer(peerId:, fromId: peer.id, …)`) and works in exactly those groups. The real constraint is `SearchMessages.swift:251`, `transaction.getPeer(fromId).flatMap(apiInputPeer)`: the author must already be in the local store with an access hash, which is why the long-press path works — the user posted, so the peer arrived cached with the message. **The failure is silent:** with no peer, `fromId` is dropped and the request goes out with no author filter at all, returning the whole chat instead of nothing, so any entry point here must never hand back a peer the search cannot use. Achievable: **`@username` works for anyone**, member or not, via `resolvePeerByName` (`ResolvePeerByName.swift:16`), which caches the peer with its access hash; **an author already in the local store works with no network**; **a bare numeric id only if that peer happens to be cached**, since an `InputPeer` cannot be built without an access hash. `inputPeerUserFromMessage` (`Api12.swift:297`) resolves a user from a message they appear in, but needs a message id from that user — the same chicken-and-egg as long-press, so it adds nothing for someone never seen. **Status: fork logic written** (`src/swift/ClearGram/TelegramUI/ClearAuthorSearch.swift`, toggle `searchHiddenMembers`, live row in Settings ▸ Search); the one stock hunk — swapping the `searchPeerMembers` call at `ChatInterfaceStateContextQueries.swift:492` for `clearSearchAuthorSuggestions` — is not applied yet.
