| ✅ `feature__settings-transfer` | export / import the Cleargram settings as a `.cleargram` file (Cleargram Settings ▸ Backup). | ✅ `feature__clear-settings-ui` | "Cleargram" entry in Settings, opening `ClearSettingsController` (fork file in `src/swift/ClearGram/DebugSettingsUI/`). Home for every `ClearConfig` toggle. Laid out like stock Telegram settings: a hub of icon rows (rendered with the stock `renderSettingsIcon`) opening per-area screens — Appearance, Chat List, Tab Bar, Chats, Channels, Media & Stickers, Links, Message Menu, Profile, Privacy, Debloat — plus a destructive Reset with a confirmation alert. Each group carries a footer explaining what it does; some footers are computed from the current value, so they read as a live preview (timestamp sample, cleaned-URL sample, music subtitle sample). The screen tree is **data**, declared in `clearRootScreen()` at the bottom of the file — `ClearScreen`/`ClearSection`/`ClearToggle` values with `WritableKeyPath` storage; a generic entry enum handles ids, equality and item construction, so adding an option is one `ClearToggle(...)` line. Unimplemented toggles are declared via `ClearToggle.soon(title:plan:)` and render disabled with the plan as a subtitle. **Build stamp:** the last line on the root screen reads `Telegram 12.9.2 · upstream 6ad963e5b6 · Cleargram 31eac9a` — the upstream release, the commit the patchset is pinned to and the cleargram commit the build was assembled from. Cleargram deliberately has no version number of its own: those three values are what actually identify a build, and unlike a build counter they need no state to maintain and map straight back to the source. **Dirty builds:** an uncommitted tree adds a `+<id>` suffix (`Cleargram 31eac9a+97a74d7`) where the id is a hash of the working-tree patch — `git status --porcelain` + `git diff HEAD` + a `/dev/null` diff per untracked file, so new fork sources count too. That keeps the line an identity rather than a warning light: the same tree always hashes to the same id, and `pnpm sync` archives the patch as `build/dirty-stamps/<commit>+<id>.diff` (gitignored, and appliable as-is), so whatever is running on a device can be reconstructed with `git apply` — which doubles as the recovery path when uncommitted work is lost. A timestamp or a counter would order builds but say nothing about their contents, and a timestamp inside a Bazel input would rebuild the module on every sync. It comes from `ClearBuildInfo`, a fork file that ships with placeholder values and whose worktree copy `pnpm sync` overwrites with the real ones (`writeBuildInfo` in `scripts/lib.ts`, run right after the copy loop that lays the placeholder down — the placeholder is what stops a sync that didn't run from breaking the build). It lives in DebugSettingsUI, next to the screen that reads it: the file changes with every commit, and in TelegramUIPreferences — which nearly everything depends on — that would invalidate the whole tree. No build-time values go in it (a timestamp would rebuild the module on every build), and nothing touches `Make.py`, `Telegram/BUILD` or the plist. |

**Search:**
- `search-by-user-id` — search messages in a group/chat by author user-id, bypassing the "hidden members" restriction. When a group hides its member list, Telegram's in-chat search (`@username` filter) breaks — the server refuses to resolve usernames of non-members. This feature adds a "search by user id" entry point (manual numeric id input, or a list of known authors derived from already-loaded messages) and runs `messages.search` with `from_id` set to the target peer. **Hybrid approach:** (1) Try `context.engine.messages.searchMessages(location: .peer(peerId, fromId: targetId, ...))` — server-side search with `from_id` may work even when members are hidden (server filters by peer id, not member-list visibility). (2) Fallback: local filter of already-loaded history by `message.authorId == targetId` in Postbox, with progressive load + progress UI if the chat isn't fully cached. **RESEARCH NEEDED:** verify whether `messages.search` with `from_id` actually works for groups with hidden members (server may still reject if the requester can't see the target peer — needs `accessHash`). If `accessHash` is required, the local cache may hold it for peers that have appeared in the chat history; otherwise the bare-id path (`tg://user?id=`) may need to be used to resolve + cache the peer first. Touches: `ChatHistorySearchContainerNode` (UI for id input / author picker), `SearchMessages.swift` (already passes `fromId` to `Api.messages.search` — may just work), new fork file `ClearUserSearch.swift` for the hybrid logic.
